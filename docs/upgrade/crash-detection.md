# 崩溃检测与事后分析

## 用户体验

每次应用启动后异步检查“上次检查点到现在”的 Windows 系统事件：

- 无新的崩溃证据：不弹窗、不创建空案例。
- 有新的 BSOD、意外关机或异常重启证据：建立案例，先保护证据时间窗，再分析并在“崩溃检测”页面显示。
- 证据不完整：标记置信度和缺口，不把异常退出直接宣称为蓝屏。

## 事件证据

首版重点归一化常见 Windows Event Log 信号，例如 BugCheck、Kernel-Power、EventLog 非正常关机和正常启动/关机边界。事件 ID 只能作为信号之一，需结合 boot session、时间关系、BugCheck code/minidump 是否存在和 clean shutdown marker 分类。

读取游标使用 channel + record id/时间双重保护；原始事件摘要落入 `system_event` 并唯一去重，保证每次启动扫描幂等。系统日志访问失败只影响 crash 功能，不阻塞主采集。

## 案例与证据窗

默认候选窗口为崩溃前 30 分钟至崩溃后 5 分钟；实际后段通常跨 boot session，用于观察恢复后的启动压力。建立 `crash_case` 后立即创建 `retention_hold`，常规清理不得删除窗口内 raw system/process samples 和关键 system events。

保留策略应限制受保护案例数量或总空间；释放必须显式记录。用户删除案例时，先解释这会解除保护，原始数据仍由普通保留策略异步清理。

## 分析管线

1. 识别崩溃时间、类型、boot 边界和证据完整度。
2. 加载窗口内系统曲线、Provider health、写入延迟和进程 Top-N。
3. 计算基线与异常：持续高 CPU/GPU、内存逼近容量、功耗/温度峰值、磁盘 I/O 饱和、采样中断、特定进程资源突增。
4. 生成结构化 `crash_finding`，附规则 id、观察值、比较基线、时间范围、证据引用、严重度和限制。
5. UI 将 findings、原始曲线和系统事件按时间对齐，不隐藏未知区间。

资源异常与崩溃之间通常只有相关性。文案使用“观察到”“可能相关”“数据不足”，不得将温度或某进程直接描述为确定根因。若存在 BugCheck code 或 dump，只展示可验证信息；深入 dump 解析属于后续可选模块。

## 分析版本

`crash_case.analysis_version` 与每个 finding 的 `rule_version` 固化生成逻辑。算法升级可重新分析同一证据窗，保留旧结果或原子替换并记录时间，避免历史 UI 因规则变化无法解释。

## 测试策略

- 单元测试：事件组合分类、窗口裁剪、去重、置信度和规则计算。
- Fixture：导出的脱敏 Windows 事件与合成资源曲线。
- 集成测试：强杀采集进程、模拟未封口区间、数据库忙/写入失败。
- 真正 BSOD/强制重启：只在一次性虚拟机或专用测试机执行，并明确快照与恢复步骤。

## 验收

- 重复启动不会重复创建同一案例。
- 发现案例后，保留任务无法删除其证据窗。
- 没有系统事件读取权限时，应用仍正常运行并给出可操作状态。
- 每条结论可追溯到指标、时间范围或系统事件，且明确置信度。
